Components

Drag

A reorderable list. Items can be dragged, but dragging is never the only way — each item also carries Up / Down buttons, the single-pointer alternative required by WCAG 2.5.7 Dragging movements. Use it anywhere users put things in an order: a Columns panel, a list of sections, or nested Stages → Tasks → Fields.

Overview

The list pairs a drag grip with Up / Down buttons. Moving an item — by drag, click or keyboard — keeps focus on the control pressed and announces the new position through a polite aria-live region. The logic lives in the hbReorder() Alpine helper (drag.js); the markup is plain hb-drag classes.

Anatomy

1
Listhb-drag — the reorderable container. One array of items in hbReorder() backs it.
2
Itemhb-drag__item — a draggable row; gets is-dragging / is-drop-target while a drag is in progress.
3
Handlehb-drag__handle — the grip for pointer dragging. Decorative (aria-hidden); never the only way to reorder.
4
Contenthb-drag__content — the item label or arbitrary content (it can hold a nested list).
5
Move buttonshb-drag__move + two hb-drag__move-btn — the single-pointer / keyboard reorder. Disabled at the ends; each names its item.

Behaviour

accessibility_new
How it satisfies WCAG 2.5.7.
  • Dragging (mouse & touch) works in parallel, but every reorder is also a single click on an Up or Down button — no dragging required.
  • Up / Down are disabled at the ends of the list.
  • After a move, focus stays on the button pressed (or its sibling if that one became disabled), and the new position is announced through an aria-live="polite" region.
  • Each button's accessible name includes the item — “Move Risk factors up”, not just “Move up”.
  • Nested lists reorder independently: moving a field never disturbs the tasks around it.

Panel variant — controls always visible

The default: Up / Down buttons are always shown next to every item. Use it inside a dedicated management panel — where the whole point of the surface is arranging things — such as the table Columns panel. This is the same pattern that panel is built from.

view_column Columns

Inline variant — reveal on hover / focus

Add hb-drag--inline for short lists (5–10 items) embedded directly in the content, with no panel around them. The grip and buttons stay hidden until the row is hovered or keyboard-focused, so the list reads cleanly at rest. The buttons remain in the tab order — a keyboard user Tabbing through the row reaches them and they appear on focus — so the single-pointer alternative is never lost.

Hover a row — or Tab into it — to reveal the grip and buttons.

Nested lists

Items can contain their own hb-drag. Each list passes its own array to the move buttons and to drop, so reordering one level never touches another — the model behind Stages → Tasks → Fields. Here a list of tasks (inline) holds a nested list of fields under the first task.

Reorder the tasks, or the three fields under the first task — each stays within its own list.

Accessibility

A drag interaction is only accessible when it has a single-pointer alternative (WCAG 2.5.7). Keyboard support alone is not enough.

check Do
Offer Up / Down buttons alongside the drag handle, always operable with a single click.
Name each button after its item, so the target is clear out of context.
Keep focus on the pressed control and announce the new position via aria-live.
In the inline variant, reveal controls with opacity so they stay focusable by keyboard.
close Don't
Make dragging the only way to reorder.
Hide the reveal-on-hover controls with display:none — it drops them from the tab order.
Label the buttons only “Move up” / “Move down” with no item name.
Let a drag in one nested list drop into another level.
info
Out of scope for now: “Move to top / bottom” shortcuts. They aren't needed while lists stay short (5–10 items); revisit if a use case grows to long lists, where repeated single-step moves become tedious.
