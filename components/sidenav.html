Components

Sidenav

The secondary navigation inside a page — the list of sections of a Profile, a Case or Settings. It shares the surface of the content it navigates: no background of its own, no dividing line. Items can carry an icon, a count and a submenu, and the nav can be collapsed away entirely, handing its width to wide content such as a table and floating back when it is hovered.

Overview

One item per page section. The current section is marked by a grey fill and a heavier weight — never by colour alone. A submenu breaks a section into its sub-sections.

Anatomy

1
Areahb-sidenav-area — the nav plus the content it belongs to. Required: it is what the collapsed nav floats over.
2
Navhb-sidenav — the container. 240 px wide; override with --hb-sidenav-width. No header and no title: the page already has one.
3
Togglehb-sidenav__toggle — collapse / expand control. Lives in the page header, before the title or breadcrumb.
4
Section labelhb-sidenav__section — uppercase label above a group of items.
5
Itemhb-sidenav__item (--active / --disabled) — one page section. Always a link: every item goes somewhere.
6
Iconhb-sidenav__icon — optional leading Material icon.
7
Labelhb-sidenav__label — the item text; truncates rather than wraps.
8
Counthb-sidenav__count — optional record count, trailing the label.
9
Submenuhb-sidenav__submenu + hb-sidenav__subitem (--active) — sub-sections in caption bold, hung off a rail line. Shown when the parent is the current section; no chevron, nothing to expand.

Items and icons

An item is a plain label at minimum. Add a leading icon when the nav lists destinations of different kinds — Settings does, a Profile's sections do not. Whichever you choose, apply it to every item in the nav: one icon among plain labels reads as an error.

With counts

A hb-sidenav__count after the label tells how many records a section holds, so the user knows what is worth opening before opening it. Use it only where the number changes something — and leave the count off rather than showing a 0: an empty section is better told by the empty state inside it.

Submenus

A section with sub-sections lists them underneath, hung off a rail line, in caption bold — one step down from the parent. There is no chevron and nothing to expand: the submenu appears because its parent is the section you are in, and disappears when you leave. The active sub-item darkens its own segment of the rail. Keep nesting to one level.

info
Because the submenu is tied to the current section, the parent of a current sub-item is always --active as well. That pair — parent filled, sub-item marked on the rail — is what tells the user where they are.

Collapsing

Wide content — a table with ten columns — competes with the nav for horizontal space. Collapsing hands that space back. Nothing is left behind: no rail, no strip of icons. The nav leaves the layout entirely, and the only thing that stays is its toggle.

It is not gone, though. Hovering the toggle floats the nav back over the content, live and clickable, so jumping to another section never costs a click on the way. Move away and it retreats; click the toggle and it is pinned open again. Same pattern as Notion's sidebar.

Where the toggle goes

The nav has no header of its own, so the toggle lives in the page header — the band that runs above both the nav and the content — pinned to its left edge, over the nav's own column. That band exists on every page: on Settings it holds the section title, on a Profile it holds the avatar, the name and its tags. A page with no title of its own still has it, and the toggle simply becomes its first element.

warning
Keep that header outside hb-sidenav-area. The area is what the collapsed nav floats over, so a toggle placed inside it ends up underneath the peek panel — the way back hidden exactly when it is needed.

No page title here — the toggle is simply the first thing in the header.

Two classes carry the whole behaviour: is-collapsed takes the nav out of the layout and hides it, and is-peeking floats it back. A short delay on leaving keeps the panel from flickering while the pointer travels from the toggle to the nav.

<div x-data="{ collapsed: false, peek: false, timer: null,
             show() { clearTimeout(this.timer); this.peek = true },
             hide() { clearTimeout(this.timer); this.timer = setTimeout(() => this.peek = false, 200) },
             pin()  { clearTimeout(this.timer); this.collapsed = !this.collapsed; this.peek = false } }">

  <!-- page header — OUTSIDE the area, so the peek panel never covers it -->
  <header>
    <button type="button" class="hb-sidenav__toggle"
            :aria-expanded="!collapsed" aria-controls="settings-nav"
            :aria-label="collapsed ? 'Expand navigation' : 'Collapse navigation'"
            @mouseenter="collapsed && show()" @mouseleave="collapsed && hide()"
            @focus="collapsed && show()" @blur="hide()"
            @click="pin()">
      <span class="hb-icon" aria-hidden="true"
            x-text="collapsed ? 'last_page' : 'first_page'"></span>
    </button>
    <h1>Settings</h1>   <!-- or the record's name, or nothing at all -->
  </header>

  <div class="hb-sidenav-area">
    <nav class="hb-sidenav" id="settings-nav" aria-label="Settings"
         :class="{ 'is-collapsed': collapsed, 'is-peeking': collapsed && peek }"
         @mouseenter="collapsed && show()" @mouseleave="collapsed && hide()">
      <!-- items -->
    </nav>
    <main> … </main>
  </div>
</div>
info
Remember the choice. A user who collapses the nav to read a wide table expects it to stay collapsed on the next page — persist the state (localStorage) per user, not per page.

Behaviour

accessibility_new
What the markup has to carry.
  • The container is a <nav> with an aria-label — a page often has two navs (the app rail and this one), and they must be told apart.
  • Every item is an <a> — there is nothing to expand, so nothing needs aria-expanded except the collapse toggle. A submenu is a plain <ul> nested under its parent item, which is how a screen reader learns the two are related.
  • The current item is marked with aria-current="page", not only with the --active class — fill and weight are for the eye, aria-current is for the screen reader.
  • A collapsed nav is hidden with visibility, so its links leave the tab order — no focus ever lands on something invisible.
  • Hover-to-peek is a shortcut for pointer users, never the only way in: the toggle is a real button that expands the nav on click or Enter. It also peeks on focus, so a keyboard user sees what they are about to open.
  • The toggle's own name changes with its state — “Collapse navigation” / “Expand navigation” — and it carries aria-expanded.
  • Icons are decorative (aria-hidden); the label carries the meaning.
  • Transitions are dropped under prefers-reduced-motion.

Guidelines

check Do
Offer the collapse toggle wherever the nav sits next to a table or another wide surface.
Keep the toggle in one place — the page header — instead of moving it in and out of the nav.
Let the peeking nav be fully usable — a user should be able to navigate from it without pinning it first.
Show a count only where the number is worth acting on.
Keep the current sub-item's parent marked as active as well.
Persist the collapsed state across pages.
close Don't
Leave a strip of icons behind — collapsed means collapsed, the content gets the full width.
Make hover the only way to bring the nav back.
Put the toggle inside hb-sidenav-area — the peek panel would cover it.
Put a chevron on a section that has sub-sections — they are not a dropdown, they belong to the section you are in.
Nest more than one level of submenu; flatten the section instead.
Use this for the app's primary navigation — that is the global rail, a different component.
Signal the current item by colour alone, or show a count of 0.
