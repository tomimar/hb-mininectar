Table

Tables present structured data in rows and columns. In Nectar, the row itself is never the control: every action lives in a cell as a real link or button. This keeps tables operable by keyboard and screen reader, gives each action its own clear target, and follows the accessibility guidance from our Level Access review.

Overview

A complete table combines a focusable scroll region, a caption, row selection, a primary link in the row-header column, and explicit row actions. Everything below builds on this base.

Anatomy

Region wrapperA focusable scroll container around the table, so a wide table can be scrolled with the keyboard alone.
2
CaptionA title that names the table for screen readers. It can stay visually hidden.
3
Column headersEvery column has a header, including a visually-hidden one for the actions column.
4
Row headerThe identifier column acts as the row's header and holds the primary link.
5
Row actionsExplicit icon buttons in the last column, named after the row they act on.

Primary action

The main action of a row — usually navigating to its detail view — is a real link in the row-header cell, built with the Link component. It is underlined by default, so it is discoverable without relying on hover.

Expandable rows

To progressively disclose more content, a disclosure button at the start of the row toggles a detail row underneath. This is the accessible replacement for a clickable row that expands. The revealed content can be a single block of detail, or several rows of related data.

Whole-row click — opt-in

If a large click target is worth it, hb-table--row-link stretches the row-header link across the whole row while the semantics stay intact. Other real controls (checkboxes, action buttons) still keep working.

Trade-off: text in the other cells can no longer be selected or copied. Avoid this variant on data-dense tables where users copy values such as transaction IDs or amounts — use the plain primary link instead.

Grid lines

Tables come in two variants. By default, cells are separated by a full grid — horizontal and vertical lines, spreadsheet-style, which helps when users read and compare individual values across many columns. hb-table--plain removes the vertical lines for a lighter look when rows are scanned as a whole.

Footer — optional

For tables with many rows or multiple pages, an optional footer sits below the table with a row-count summary, a page-size Select and a status line on the left, and pagination controls on the right. It lives outside the table's border, as a sibling of the scroll region.

Accessibility

The rules behind this component, straight from the Level Access review.

Do
Give every action its own visible link or button inside a cell.
Name repeated actions after their row, so "Edit" always says which item it edits.
Keep the identifier column as the row's title, holding the primary link.
Make interactivity visible without hover — underlined links, visible buttons, focus rings.
Don't
Make clicking somewhere in the row the only way to act on it.
Reveal actions only on mouse hover.
Hide the row's primary action inside the overflow menu.
Use the whole-row click variant where people need to select or copy cell values.
